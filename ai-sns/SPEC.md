## 1. コンセプト

- 「架空のSNS」をスマホアプリで遊ぶ。登場するフォロワー・リアクションはすべてAI(LLM)が生成する。
- フォロワーは最初 **0人**。ユーザーがつぶやくたびに、内容に興味を持った **架空の20人** が少しずつフォローしてくる。
- 20人にはそれぞれ **個性(職業・性格・口調・関心領域)** があり、自分の関心が強い話題には食いつき、関心のない話題には反応しない。
- **一度フォローしたフォロワーは外れない。** 安心して育てられる。
- **誰でも参加できる。** 20人のフォロワーは全ユーザー共通の「住人」で、あなたのフォロワーは他の人のフォロワーでもある。ただし **ユーザー個人同士は一切つながらない**(§3.6)。
- 「何をつぶやくと誰が来るか」を試して、**自分のつぶやきでフォロワーが育っていく手応え** を楽しむ。

### 1.1 ゴール / 非ゴール

| ゴール | 非ゴール |
|---|---|
| つぶやき投稿 → フォロワー増加 → リアクション(いいね・返信)の一連の体験 | **ユーザー同士のつながり**(フォロー・DM・投稿閲覧・ユーザー検索・フレンド機能)は恒久的に作らない |
| 20人の個性が会話から明確に伝わること | 実在の人物・企業・SNSの模倣 |
| 話題によって集まるフォロワーが変わること | 広告・課金(v1) |
| 複数ユーザーが同じ20人を共有しても、各人の体験・記憶が混ざらないこと | フォロワーのリムーブ(外れる仕様) |

## 2. 用語

| 用語 | 意味 |
|---|---|
| つぶやき | ユーザーの投稿(最大140字想定) |
| ペルソナ | 20人のフォロワーそれぞれのキャラクター定義。**全ユーザー共通** |
| 関係(リレーション) | 「ユーザー × ペルソナ」ごとの状態(フォロー済みか、親しさ、会話の記憶)。**ユーザーごとに独立** |
| 関心トピック | 話題の分類タグ(例: 料理、ランニング、プログラミング) |
| 親和度(affinity) | つぶやき内容とペルソナの関心の一致度(0〜1) |
| 候補プール | そのユーザーをまだフォローしていないペルソナ(最初は20人全員) |

## 3. 主な機能

### 3.1 つぶやき投稿
- テキスト入力(140字)→ 投稿でタイムラインに追加。
- 投稿直後に「話題解析 → フォロー判定 → リアクション生成」がサーバー側で走る(§5)。

### 3.2 フォロワーの増加
- 投稿ごとに、**そのユーザーの**候補プールの各ペルソナについてフォローするか判定。
- 1投稿で増える人数は **最大3人**(小出しにする)。
- 新規フォロワーは「〇〇さんにフォローされました」の通知と、フォローのきっかけになった一言コメントを返す。
- 話題が合わなければ0人の投稿もある(それも楽しみのうち)。
- **フォローは永続。** 放置しても、どんな話題をつぶやいても外れない。20人全員がフォロワーになったらコンプリート。

### 3.3 リアクション
- フォロワーは投稿に対して以下を行う:
  - **いいね**: 親和度が中程度以上
  - **返信**: 親和度が高い / 「強い関心トピック」に触れた場合(ほぼ確実に返信)
  - **スルー**: 関心がない場合(フォロワーが外れることはない)
- 返信は各ペルソナの口調で生成(§4)。
- ユーザーは返信にさらに返信でき、その場合は同じペルソナが会話を続ける(スレッド形式)。

### 3.4 画面(v1)
1. **タイムライン**: 自分のつぶやき+付いたリアクション・返信
2. **フォロワー一覧**: 20人分のカード(フォロー済みは通常表示、未フォローは「???」のシルエット)
3. **プロフィール詳細**: 名前・ID・年齢・職業・自己紹介・好きな話題・自分とのやりとり(他ユーザーに関する表示は一切なし)
4. **通知**: 新規フォロー・いいね・返信(アプリ内+プッシュ通知)
5. **設定**: ニックネーム、データ削除、利用規約・プライバシーポリシー

### 3.5 将来拡張(v2以降の候補)
- 全員フォロー後の遊び(親密度レベル、お気に入りフォロワー、フォロワー限定の話題イベント)
- フォロワー同士の会話(同じ話題で盛り上がる / 意見が割れる)
- フォロワー自身の「つぶやき」がタイムラインに流れる
- 画像付き投稿、ペルソナとのDM、ハッシュタグ、フォロワー数のグラフ

### 3.6 マルチユーザー(共有フォロワー)

**考え方**: 20人のペルソナは世界に1セットだけ存在し、全ユーザーが同じ20人を取り合う…のではなく **共有する**。AさんをフォローしているケンジがBさんもフォローしている、という状態になる。

| 項目 | 仕様 |
|---|---|
| ペルソナ定義 | 全ユーザー共通(同じ名前・性格・口調)。1人のペルソナが多数のユーザーに同時にフォローされうる |
| フォロー状態 | `ユーザー × ペルソナ` ごとに独立。Aさんのフォローが増えてもBさんには影響しない |
| 会話の記憶 | ユーザーごとに完全分離。ペルソナはAさんとの会話をBさんとの会話で一切参照しない |
| 見えるもの | 自分と、自分のフォロワー(ペルソナ)とのやりとりだけ。人数などの集計も表示しない |
| 見えないもの | 他のユーザーの存在・名前・ID・つぶやき・フォロワー構成・活動 |
| やらないこと | ユーザー同士のフォロー/DM/検索/ランキング/投稿の共有。ペルソナ経由での内容の漏洩(「他の人もこんなこと言ってたよ」等) |

**実装上の約束(プライバシー境界)**
- LLMに渡すプロンプトには **そのユーザー自身のデータだけ** を入れる(他ユーザーのつぶやき・会話を絶対に混ぜない)。
- システムプロンプトに「他のユーザーの存在や内容には言及しない」を明記し、出力検査でも「他の人」系の表現を検出する。
- ユーザー識別子は匿名(端末ごとに発行した乱数ID)。メールアドレスなどの個人情報は取得しない。
- **ユーザー同士は、Xで互いにブロックし合っている状態と同じ扱い。** 相手の存在を示す手がかり(人数、「他にも〜」の表示、共通のフォロワー表示、ランキング、おすすめなど)を画面にもAPIにも一切出さない。ペルソナも他ユーザーに言及しない。

## 4. フォロワー(ペルソナ)設計

### 4.1 ペルソナのデータ項目(全ユーザー共通のマスタ)

| 項目 | 内容 |
|---|---|
| id / 表示名 / @ハンドル | 例: `kenji_run` |
| 属性 | 年齢・職業・住まい(ざっくり) |
| 性格 | 3語程度(例: 熱血・世話好き・単純) |
| **関心トピック** | `strong`(強い関心)/ `mid`(中)/ `weak`(弱)/ `dislike`(苦手)をタグで保持 |
| **口調** | 一人称、語尾、口癖、絵文字の頻度、敬語/タメ口、方言、禁止表現 |
| 気難しさ `θ` | フォローの閾値(高いほど簡単にはフォローしない) |
| 反応傾向 | いいね率・返信率・文章量(短文/長文) |
| 活動時間帯 | 返信が返ってくる時間の演出用(任意) |
| 口調サンプル | 実際のセリフ例を3〜5個(LLMへのfew-shot用) |

※ ユーザーごとの状態(フォロー済みか、会話履歴など)はこのマスタには持たず、§6の `relations` に持つ。

### 4.3 フォロワーとの距離感(決定)
**フォロワーは、SNSで見かけただけの「よく知らない人」。リアルの友達ではなく、会ったこともない。**

- 実際に会う・一緒に何かする誘いはしない(「会おう」「今度一緒に」「オフ会」など)。会える前提の話もしない
- 相手の私生活・過去・性格を知っている前提で話さない(「いつも」「前に言ってた」など、共有した過去を匂わせない)。相手の名前も呼ばない
- 踏み込みすぎない。健康・食事・恋愛・家族などを詮索したり、世話を焼いたり、説教したりしない
- ただし冷たくはしない。SNSで見かけたつぶやきに反応する、ほどよい距離で、軽い共感・感想・ちょっとした質問をする
- 新しくフォローしてきたときは、「つぶやきが気になってフォローした」くらいの軽い一言(馴れ馴れしくしない)
- 実装: AIへの指示(`src/llm/prompts.ts`)、キャラのセリフ例・口癖・プロフィール(`data/personas.json`)、返信の検証(会う誘いを弾く。`src/llm/verify.ts`)の3か所で守る。テストで、セリフ例に誘い・私生活への踏み込みが無いことも確認している

### 4.4 口調の維持ルール
- ペルソナごとに **システムプロンプトの口調ブロック** を固定し、毎回同じ定義を渡す(全ユーザー共通の定義)。
- 返信は **ペルソナの文章量設定** に従う(例: ショウは1文、トオルは3文)。
- 禁止: 全員が同じ文体になる / 丁寧な「AIっぽい」定型文(「素晴らしいですね!」の連発)/ 他人を攻撃する内容。
- そのユーザーとの過去の返信を直近N件(5件程度)プロンプトに含め、口癖と話の継続性を保つ。

## 5. 仕組み(ロジック) ※サーバー側で実行

### 5.1 全体フロー

```
アプリ → サーバーへ投稿
  │
  ① 事前チェック ── 文字数/投稿回数の上限
  ② 保存して即返答 ── 投稿を status='processing' で保存し、すぐ 201 を返す(アプリは待たされない)
  │
  ── ここから裏で処理(waitUntil)──────────────────────────
  ③ 話題解析 ── トピックタグ+重みを抽出(LLM。失敗時はキーワード一致)
  ④ フォロー判定(ルールベース+乱数) ── そのユーザーの候補プールから最大3人
  ⑤ リアクション判定(ルールベース) ── 無視 / いいね / 返信 を決定
  ⑥ 返信生成(LLM) ── 返信するペルソナ分を1回の呼び出しにまとめて生成。検証・再生成あり
  ⑦ 保存 ── 1回のバッチで、投稿を status='done' にし、フォロー・通知・リアクションを書く。
            それぞれに「表示時刻」を付ける(10秒〜最大3分後。人ごとにずらす)
  │
アプリは GET /v1/posts と GET /v1/notifications を取りに行き、表示時刻を過ぎたものだけが見える
```

- **新規フォロワーのフォロー時刻・フォロー通知・最初の返信は、同じ表示時刻にそろえる**(「フォローされました」と返信が同時に現れる)。表示時刻前のフォローは、フォロワー一覧にも人数にも出ない。
- **処理が途中で打ち切られた場合の救済**: 処理は最後に1回のバッチで書くので、途中で落ちても中途半端な状態は残らない。処理中のまま90秒たった投稿は、一覧・通知を読み出したときに検知し、**AIを使わない縮退運転**(キーワード話題解析+セリフ例の返信)で完了させる。
- 乱数は投稿IDから決まるので、やり直しても判定は同じ。

### 5.2 話題解析
- 出力例:
  ```json
  { "topics": [{"tag": "料理", "weight": 0.7}, {"tag": "節約", "weight": 0.3}],
    "sentiment": "positive", "intensity": 0.6 }
  ```
- タグは固定の語彙リスト(§4.2 の関心トピックを網羅)から選ばせ、揺れを防ぐ。
- 単純なキーワード一致でもある程度判定できるため、LLMが使えないときの縮退運転(フォールバック)に使う。

### 5.3 フォロー判定

```
親和度 affinity(f, 投稿) = Σ ( 投稿のtag重み × ペルソナの関心値 )
  関心値: strong=1.0 / mid=0.5 / weak=0.2 / 未設定=0 / dislike=-0.5

親和度 ≤ 0 なら確率 0(苦手・無関係な話題では絶対にフォローしない)

フォロー確率 P = pace × sigmoid( slope × ( affinity − (θ_f + thresholdShift) ) ) + 人気の上乗せ
  pace=0.6(合っていても最大60%。毎回は来ない)/ slope=10 / thresholdShift=0.2
  人気の上乗せ: 現在のフォロワー1人につき+1%、最大+10%(「人気の人にはフォローしやすい」演出)
  上限: P ≤ 0.95

ひとめぼれ: strongトピックが重み0.5以上で含まれる場合は P ≥ 0.55
```
- 対象は **そのユーザーが未フォローのペルソナだけ**。確率で当落を決め、当選者のうち親和度上位 **最大3人** を採用。
- 他のユーザーの状況は P に一切影響させない(§3.6)。
- 乱数は「投稿ID+ペルソナID」から決まるシード付き。同じ投稿なら同じ結果で、他の人が既にフォロー済みでも各人の当落は変わらない(再現性・テスト用)。
- **フォロー解除の処理は存在しない。**
- 設定値は `server/src/follow.ts` の `DEFAULT_FOLLOW_CONFIG` に集約。`npm run sim` で、AIを使わずに増え方を確認しながら調整できる。

**シミュレーション結果(3000人分、キーワード話題解析・サンプル投稿58件。実際の投稿はもっと偏るので目安)**

| 投稿の傾向 | 5投稿後 | 10投稿後 | 30投稿後 | 100投稿後 |
|---|---|---|---|---|
| いろんな話題 | 平均 4.6人 | 8.6人 | 16.9人 | 19.9人(コンプリートの中央値は55回目) |
| 運動の話ばかり | 2.4人 | 3.1人 | 3.8人 | 4.0人で頭打ち |
| 食べ物の話ばかり | 4.3人 | 6.2人 | 8.9人 | 10.7人 |
| 日常の雑談ばかり | 3.5人 | 5.4人 | 10.0人 | 12.0人 |

→ 1つの話題だけでは頭打ちになり、**いろんな話題をつぶやくほど増える**。実際の増え方はM3以降(LLMの話題解析)で再確認する。

### 5.4 リアクション判定
- フォロー済みペルソナ全員について、親和度 ≥ 高閾値 → 返信、≥ 中閾値 → いいね(+低確率で返信)、それ未満 → 無視。
- ペルソナごとの「返信率/いいね率」で最終確率を補正。
- 1投稿あたりの返信は **最大5件** に絞る(画面が埋まらず、LLMコストも抑えられる)。
- いいねは **LLMを使わずルールだけ** で生成(コストゼロ)。

### 5.5 返信生成(LLM)
- 入力: 返信するペルソナ(最大5人)の口調定義、つぶやき本文(`<post>` で囲み、本文中のタグ破りは無害化)、話題解析結果、**そのユーザーとの**直近3件のやりとり、「新規フォロー時か」フラグ。
- 出力: `{"replies":[{"personaId":..., "text":...}]}` のJSON(複数人まとめて1リクエスト)。JSONスキーマで形式を強制し、読めない場合も `<think>`・フェンス・前後の説明文を除いて取り出す。
- 検証(`src/llm/verify.ts`)。次の違反があれば、**違反した人だけ**を再生成する(最大2回):
  - 空、または文字数超過(短文キャラ70字 / 標準140字 / 長文240字)
  - 絵文字を使わないキャラが絵文字を使っている
  - 一人称がキャラと違う(私/わたし、俺/おれ、僕/ぼく は同じ扱い)
  - AI・プロンプト等への言及(つぶやき自体がその話題なら許容)
  - 他のユーザーへの言及
- それでも通らない場合は、キャラのセリフ例で代用する(返信ゼロにはしない)。通信エラー・設定ミス・安全判定による拒否のときは、全員セリフ例で代用して投稿自体は成功させる。
- いいねは**LLMを使わず**確率だけで決める(§5.4)。リアクションは `visible_at`(10秒〜最大3分後)まで一覧に出さない(時間差演出)。

## 6. データモデル(案)

| テーブル | 主なカラム | 備考 |
|---|---|---|
| `users` | id(乱数), nickname, created_at, daily_post_count, … | 個人情報は持たない |
| `personas` | id, name, handle, profile(JSON), interests(JSON), theta, reaction_profile | **全ユーザー共通のマスタ**。ファイル(`personas.json`)で管理し起動時/デプロイ時に投入 |
| `posts` | id, user_id, body, topics(JSON), created_at, **status**(`processing`/`done`), **process_started_at** | 自分の投稿のみ参照可。処理中のまま止まった投稿の検知に使う |
| `relations` | user_id, persona_id, followed_at(**表示時刻。未来なら予約中で、一覧・人数には出ない**), trigger_post_id, affinity_at_follow, intimacy | **ユーザー×ペルソナ**。ここが「誰が誰をフォローしているか」の唯一の正。削除(外れる)処理は存在しない |
| `reactions` | id, user_id, post_id, persona_id, type(`like`/`reply`), text, visible_at | `visible_at` を過ぎたら表示(時間差演出) |
| `threads` | user_id, 親reaction_id, 子reaction/ユーザー返信 | ユーザーとペルソナの会話 |
| `notifications` | id, user_id, type, ref_id, read, created_at | |
| `persona_stats` | persona_id, follower_count | 運営用の内部集計(任意)。アプリ・APIには出さない |

- すべてのクエリは **`user_id` で絞る**(他ユーザー行を読む経路を作らない)。ユーザー間をまたぐ参照は作らない。

## 7. 技術構成(おすすめ・低コスト重視)

### 7.1 推奨構成

| 項目 | 推奨 | 理由 |
|---|---|---|
| スマホアプリ(**Androidのみ**) | **Kotlin + Jetpack Compose** | Android専用なので公式推奨のネイティブが最も素直で、動作も軽い。プッシュ通知は FCM(無料)。最小対応は既存 `nippo-app` に合わせて Android 8.0(minSdk 26)を想定。※ 既存の `nippo-app` は Java 製だが、新規アプリは Kotlin で作る。将来 iOS も出すなら Expo(React Native)へ切り替える選択肢あり(サーバー側は変更不要) |
| サーバー | **Cloudflare Workers + D1(SQLite)** | 小規模なら無料枠で動かせ、常時稼働のサーバー代がかからない。使った分だけの課金。認証・DB・API を1か所にまとめられる |
| 認証 | **匿名ログイン**(端末で発行した乱数ID+サーバー発行トークン) | メール/パスワードなし=個人情報を持たない。後から Apple/Google でのアカウント引き継ぎを追加可能 |
| LLM | **Claude Haiku 5.5**(`claude-haiku-5-5`) | 現行モデルで最安クラス。入力 $0.10 / 出力 $0.50 (100万トークンあたり、プロンプト10万トークン以下)。短いキャラ返信には十分な品質 |
| 呼び出し方 | サーバー側から Anthropic SDK(`@anthropic-ai/sdk`)で呼ぶ。**APIキーはアプリに入れない** | キー漏洩防止。ユーザーごとの回数制限もサーバーでかけられる |
| 時間差演出 | 返信に `visible_at` を付けてDBに保存、アプリが取得して表示 | キューやバッチ基盤が不要。応答を遅らせる演出がそのままコスト削減(下記)に使える |

> 候補比較: Firebase(Firestore+Functions)も同様に作れるが、サーバー処理を使うには従量課金プランの登録が必要。Supabase も有力。ここでは無料枠で始めやすく、TypeScript一本で揃う Cloudflare を推奨。

### 7.2 LLMコストの見積り

前提: 1投稿につき LLM 呼び出しは **2回**。①話題解析(軽量: 入力 約700 / 出力 約60トークン)、②返信生成(最大5人分をまとめて: 入力 約4,000 / 出力 約600トークン。ペルソナ定義が入力の大半)。

| 規模 | 投稿数/月 | LLM費用の目安 |
|---|---|---|
| 個人/友人数十人(50人×1日3回) | 約4,500 | 約 **$4(600円前後)** |
| 1,000人×1日5回 | 約150,000 | 約 **$120(1.8万円前後)** ※下の節約策を入れる前の上限目安 |

(1投稿あたり約 $0.0008 = 0.12円。為替は1ドル150円で概算。料金は 2026-11 時点の公開価格で、**契約前に最新を要確認**)

**さらに下げる工夫(優先順)**
1. **プロンプトキャッシュ(当面は不要と判断)**: 返信するキャラ(最大5人)の口調定義だけを毎回付ける設計にしたため、入力は概算で約2,000トークン(約$0.0002)。キャッシュの効果が小さい割に仕組みが複雑になるので、利用が増えて費用が問題になってから検討する。
2. **思考(thinking)を最小化**: Haiku 5.5 はデフォルトで思考が有効。短い返信用途なので `effort: low`(または思考オフ)にして出力トークンを削る。
3. **いいね・スルー・定型通知はLLMを使わない**(ルールのみ)。
4. **返信上限(1投稿5件)、文字数上限、ユーザーごとの1日投稿上限**(例: 1日10回)。
5. **Batch API(通常の50%)**: 返信を数分〜数時間遅れて出す演出と相性が良い。ただし完了時刻が保証されないので、初期は通常APIで作り、費用が気になってから切り替える。
6. **全体の月間予算上限**を設け、超えたら「いいねだけ」の縮退運転に自動で切り替える(請求の暴走防止)。

### 7.3 固定費の目安(アプリ公開する場合)

| 項目 | 費用 |
|---|---|
| Google Play デベロッパー登録(Android公開) | 初回のみ $25 |
| 身内テスト(§9.1のフェーズ1) | APKを直接配布する場合は $0(Play登録も不要) |

| (iOS) | 対象外。将来出す場合のみ Apple Developer Program が年 $99 |

### 7.4 テスト中のLLM(ローカルLLM・モック対応)

**結論: 開発・テスト中はローカルLLMで動かせる。** サーバーのLLM呼び出しを1つの窓口(`LlmProvider`)に隠し、環境変数で切り替える。

| プロバイダ | 用途 | 費用 | 特徴 |
|---|---|---|---|
| `mock` | 画面・フォロー判定・DBなどの開発 | 無料 | LLMを使わず、ペルソナのセリフ例から決め打ちで返す。高速で結果が毎回同じ(自動テスト向き) |
| `local`(ローカルLLM) | 口調・プロンプトの試行錯誤、1人での通し確認 | 無料(電気代のみ)、APIキー不要 | 自分のPCで動かす。**OpenAI互換API(`/v1/chat/completions`)を話すサーバーなら何でも**使える(Ollama / LM Studio / llama.cpp / mlx-lm / vLLM など)。`LLM_BASE_URL` と `LLM_MODEL` で指定 |
| `anthropic`(Haiku 5.5) | 身内テスト以降、本番 | §7.2のとおり | 速い、日本語のキャラ付けが安定、PC常時起動が不要 |

**ローカルLLMを使うときの注意**
- **サーバーも手元のPCで動かす**(`wrangler dev` など)。Cloudflare 上のサーバーから自宅PCのLLMには届かない。
- 実機のAndroidからは、同じWi-Fi内のPCに接続するか、Cloudflare Tunnel 等で外から届くようにする。**その間PCは起動しっぱなし**が必要。身内の複数人が使う用途には不向き。
- 開発機: **Mac mini(M5 Pro / メモリ48GB)**。ユニファイドメモリなので、4bit量子化した **14B〜32B級** の日本語に強いモデル(Qwen系・Gemma系など。選定は着手時に最新を確認)が余裕で載る(32B級で約20GB前後)。70B級は容量的にほぼ限界で非推奨。返信は数百トークンなので、数秒〜十数秒で返る見込み(実測は着手時に確認)。
- この Mac でそのまま Android Studio(エミュレータ含む)も動かせる。実機 Android からはこの Mac に同じWi-Fi経由で接続する。Mac がスリープしないよう設定が必要。
- JSON出力が崩れやすいので、Ollama の **スキーマ指定出力(structured outputs)** を使い、崩れたら再生成する(§5.5の検証を流用)。
- 小型モデルは **口調の個性・文脈理解が Haiku より弱い** 想定。ローカルで良く見えたプロンプトが Haiku でも同じとは限らないため、キャラの最終調整は Haiku で確認する。

**使い分け(おすすめ)**
1. **M1〜M2**(土台・フォローの増え方): `mock` だけで足りる(返信生成が不要)。
2. **M3**(返信生成): まず `local` で形式・フロー・口調の大枠を作り、仕上げの口調調整は `anthropic` で。`npm run try-llm` で、サーバー無しで口調を確認できる。
3. **身内テスト以降**: `anthropic`。身内規模(約50人×1日3回)で月 $4 程度なので、ローカルで節約できる額は小さい。ローカルの主な価値は「開発中の試行錯誤が無料・APIキー不要・オフライン可」。

## 8. 非機能・安全面

- アプリ内に「登場人物はすべてAIによる架空の人物です」と明記する。
- 実在の人物・団体・SNSの名称やブランドを模倣しない。
- **ユーザー間の隔離**(§3.6): 他ユーザーのデータをプロンプト・画面・APIのどこにも出さない。APIは常に認証済み `user_id` の行しか返さない。
- **プロンプトインジェクション対策**: ユーザーのつぶやきは「データ」として区切って渡し、「命令」として扱わせない。ペルソナの口調や設定を書き換える試みは無視する。
- 攻撃的・差別的・性的な内容の入力は事前フィルタ(キーワード+LLMの安全判定)で止め、ペルソナの返信も出力検査する。アンチ/荒らし役は入れない。
- 個人情報(住所・電話番号など)を書かないよう入力欄に注意喚起。投稿はそのユーザーの返信生成のためだけに使い、他の用途に使わない。
- データ削除(アカウントと投稿の全削除)を設定画面から実行できる。利用規約・プライバシーポリシーを用意(ストア公開時は必須)。
- 悪用対策: 端末ごとの回数制限、異常な投稿頻度の検知。
- LLM障害・予算超過・安全判定で拒否された場合は、定型リアクション(いいね+定型一言)にフォールバックし、アプリは止めない。
